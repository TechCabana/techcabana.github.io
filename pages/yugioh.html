About This Project

Purpose & Motivation

I've collected Yu-Gi-Oh! cards for years, and the collection had never lived anywhere better than a shoebox and a vague memory of what was already in it. I wanted a proper catalogue — something I could search on my phone while standing in a card shop, without paying for hosting or maintaining a server to do it.

The design goal was that adding a card should mean typing one thing: the set code printed on the card, for example SDJ-017. Everything a card already knows about itself — its name, attack, defence, attribute, rarity, artwork — should be fetched rather than retyped. Logging a card takes seconds, and the site catches up on its own.

The Constraint That Shaped Everything

The repository is public, and Airtable has no read-only public API key. Any token that reaches the browser grants read and write on the entire base to anyone who opens the page source. That single fact ruled out the obvious design — fetching from Airtable in client-side JavaScript — before a line of it was written.

So the browser never talks to Airtable at all. A GitHub Action does, at build time, and commits a plain JSON file for the site to read. There is no credential anywhere in the shipped code, because there is nothing for a credential to authenticate against.

Implementation & Technical Considerations

The site itself is deliberately plain: hand-written HTML, CSS and ES modules, no framework and no build step. A hundred-odd cards on a page does not need a virtual DOM, and skipping the toolchain means nothing sits between the source and what actually ships.

The interesting engineering is in the pipeline. Enrichment looks a card up by set code rather than by name, because a set code identifies a single printing — which is how a collection is actually kept — and because name lookups need an exact match that punctuation makes fragile. Serials are trimmed before lookup, after a pasted value carrying an invisible trailing newline URL-encoded to %0A and silently broke a search.

Before the sync writes anything, it refuses results that are not an array, are empty, are missing required fields, or still contain a private field. Quantity, condition and set price live in Airtable and are stripped before publication, because the repository is public and those are inventory data. The run fails rather than publishing bad or private data. Card art is mirrored into the repository instead of hotlinked, at YGOPRODeck's request, and a single failed image is reported rather than thrown — that card falls back to a type-coloured block instead of taking the page down.

Testing & Reliability

292 Vitest tests across 13 suites cover the search and filter logic, the card markup and its escaping, the Airtable-to-card mapping including the private-field guard, pagination, incremental image downloads, and the refusal to write bad data. The suite runs without a browser and without a network.

The source tree is shaped by that requirement. Every piece of logic worth testing was pulled out of the DOM handlers and out of the network calls, which is why the filtering, the mapping and the enrichment layers are pure functions that take data and return data. One suite reads the stylesheets as text purely to enforce that no colour value is written outside the design token file; another guards the 59:86 card geometry against a fixed pixel height creeping back in.

A blocked row does not stop the run. Enrichment continues on error, so the sync, the commit and the deploy all still happen, and the job turns red at the end. Good data goes live and the problem stays visible.

Decisions Worth Explaining
Decision Why
Fetch Airtable at build time, not in the browser Airtable has no read-only key. A token in client-side JavaScript on a public repository grants read and write on the whole base to anyone who views source.
Key on set code, not card name A set code identifies one printing. Name lookup needs an exact match, and punctuation breaks it — "Blue Eyes White Dragon" without the hyphens returns nothing.
Mirror card images into the repository YGOPRODeck asks for this rather than per-view hotlinking, and it keeps the page working when their host is slow or unreachable.
Enrich in a GitHub Action, not Airtable scripting Airtable scripting needs a paid plan, and the code would live outside the repository with no tests, no review and no history.
Deploy Pages from the same workflow GitHub deliberately blocks a push made with the Actions token from triggering further workflow runs, so the data commit would land and never publish.

Design Approach

The brief I set myself was a dark theme that reads hand-built rather than generated: flat near-black layered surfaces with hairline borders, depth from layering instead of glow, and one restrained interaction accent for focus and selection.

The rule that does the most work is that colour carries meaning and never decoration. Card type maps to the real Yu-Gi-Oh! card-frame palette — Normal tan, Effect orange, Spell teal-green, Trap magenta, Ritual blue, Fusion purple — so the grid is scannable by colour alone. Every colour value lives in a single token file, and a test fails the build if one is written anywhere else. Motion is kept to 120–200ms for state changes, transform and opacity only, all of it wrapped in prefers-reduced-motion.
